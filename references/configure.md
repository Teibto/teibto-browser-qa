# ตั้งค่าระบบผ่านหน้าจอ — สัญญาที่ต่างจาก QA โดยสิ้นเชิง

QA ผิด = **รายงานผิด** · config ผิด = **ระบบจริงเปลี่ยน**

สองอย่างนี้ใช้เครื่องมือชุดเดียวกัน (`cdp.py`) แต่ต้องคนละสัญญา ถ้าเอากติกาของ QA มาใช้กับงาน
config เมื่อไหร่ จะได้ระบบที่ถูกแก้โดยไม่มีใครรู้ว่าแก้อะไรไปบ้าง

> **ข้อแรกก่อนเริ่ม: ค่าไหนตั้งผ่าน API ได้ API ชนะเสมอ**
> หน้าจอเก็บไว้สำหรับค่าที่ **ไม่มี** API ให้ตั้งเท่านั้น — เพราะ verify ผ่าน API เชื่อได้กว่า
> และไม่พังทุกครั้งที่ UI ขยับ (`cdp-limits.md` §2)

---

## 1. วงจรบังคับ 6 ขั้น

```
desired-state (ไฟล์ใน repo)
  → READ    อ่านค่าปัจจุบันจากหน้าจอ
  → DIFF    ไม่ต่าง = ไม่แตะ  ← idempotent โดยโครงสร้าง ไม่ใช่โดยความตั้งใจ
  → PLAN    พิมพ์ให้ดูก่อน (dry-run เป็นค่าเริ่มต้น)
  → APPLY   ทีละ field + shot ก่อน/หลัง
  → VERIFY  อ่านกลับจากหน้าจอ ไม่ใช่เชื่อว่ากดแล้ว
  → RECORD  หลักฐาน + ค่าเดิม + ใครสั่ง + เมื่อไหร่
```

**DIFF ก่อน APPLY คือหัวใจ** — ไม่ใช่เพื่อความเร็ว แต่เพราะการรันซ้ำแล้วไม่แตะอะไรเลยคือสิ่งเดียว
ที่พิสูจน์ได้ว่าสคริปต์เข้าใจสถานะปัจจุบันจริง สคริปต์ที่ "กดทุกช่องใหม่ทุกครั้ง" จะดูเหมือนทำงาน
ได้ตลอดจนถึงวันที่มันเขียนทับค่าที่คนอื่นเพิ่งแก้

## 2. desired-state — เขียน "ค่าที่ต้องการ" ไม่ใช่ "ลำดับการคลิก"

```yaml
# config/sb2-preferences.yaml
target:
  env: sb2                      # ต้องตรงกับ profile/port ที่เปิดอยู่
  url: /app/setup/company/generalpreferences.nl
fields:
  - name: ชื่อบริษัทที่แสดงบนฟอร์ม
    sel: "#companyname"
    want: "Teibto Co., Ltd."
  - name: รูปแบบวันที่
    sel: "#dateformat"
    want: "DD/MM/YYYY"
    how: pick                   # pick = dropdown ที่ต้องคลิกจริง (ค่าเริ่มต้น: fill)
```

- `sel` + `want` เท่านั้นที่จำเป็น · ห้ามใส่ลำดับคลิกลงไฟล์นี้ ไม่งั้นแก้ UI ทีเดียวไฟล์ตายทั้งกอง
- ค่าที่เป็นความลับ **ห้ามอยู่ในไฟล์นี้** — อ่านจาก env/`.env` ตอนรัน
- ไฟล์นี้อยู่ใน repo และผ่าน review เหมือนโค้ด — นี่คือจุดที่คนเห็นว่า "จะเปลี่ยนอะไรบ้าง" ก่อนเปลี่ยนจริง

## 3. Guardrail ที่ต้องมีตั้งแต่รันครั้งแรก

| กฎ | ทำไม |
|---|---|
| **`DIALOG=dismiss` เป็นค่าเริ่มต้นของโหมดนี้** | กลับด้านจาก QA — กด OK บน `confirm` = ยืนยันบันทึก/ลบจริง (`gotchas.md` §3) · ต้องตั้งใจสั่ง accept เป็นราย ๆ ไป |
| **prod ต้องปลดล็อกด้วย flag ที่พิมพ์เอง** | คนละ port/profile **ไม่ใช่** ด่านกันพลาด มันแค่กันการชนกัน |
| **verify อ่านกลับไม่ได้ = `UNVERIFIED` แล้ว exit** | "ตรวจไม่ได้" ไม่ใช่ "สำเร็จ" · เดินต่อทั้งที่ยืนยันไม่ได้ = แก้ระบบโดยไม่รู้ผล |
| **shot ก่อน/หลังทุก field** | หลักฐานว่าอะไรเปลี่ยน · ไม่มีภาพ = ไม่มีหลักฐาน |
| **หนึ่ง run = หนึ่งแท็บ** | คำสั่งที่ไปตกแท็บผิดใบตอน config = แก้ค่าผิดหน้าจอ |
| **ห้าม batch แบบมองไม่เห็น** | field ที่ apply แล้วไม่ verify ทีละตัว จะรู้ว่าพลาดตอนที่มันพังในระบบจริงแล้ว |

## 4. ท่ารัน

```bash
# 1) dry-run — ไม่มีอะไรถูกแก้ ได้แผนออกมาอ่าน
AB run config/read-current.txt > out/current.json
#    เทียบกับ desired-state แล้วพิมพ์ plan ให้คนอ่าน

# 2) apply (หลังคนอ่าน plan แล้วเท่านั้น)
DIALOG=dismiss AB run config/apply-sb2.txt

# 3) verify — อ่านกลับจากหน้าจอ ไม่ใช่เชื่อว่ากดแล้ว
AB run config/verify-sb2.txt > out/after.json
```

สคริปต์ apply ต้องหน้าตาแบบนี้ — **assert หลังทุก field ไม่ใช่หลังทั้งชุด**:

```
nav <url ของหน้า setup> 3
shot out/before.png
fill #companyname Teibto Co., Ltd.
get value #companyname
click #btn-save
wait document.querySelector('.messages')!==null 20
shot out/after.png
```

## 5. Evidence record

เขียนไฟล์เดียวต่อการรันหนึ่งครั้ง เก็บไว้ข้าง desired-state:

```yaml
run_id: 2026-08-16T14:20+07:00-sb2-preferences
env: sb2
by: wichit
plan_reviewed_by: <ชื่อคนที่อ่าน plan>   # prod บังคับ
changes:
  - sel: "#dateformat"
    before: "MM/DD/YYYY"
    after: "DD/MM/YYYY"
    verified: true
    shots: [out/before.png, out/after.png]
unverified: []          # ต้องว่าง ถ้าไม่ว่าง = งานยังไม่จบ
```

`before` คือสิ่งที่ทำให้ rollback เป็นไปได้ — ไม่มีมันแล้วการ "แก้กลับ" จะกลายเป็นการเดา

## 6. กับดักที่เจอแล้วในงานจริง

- **หน้าที่ต้องกด Save แยกส่วน** — บาง setup page มีปุ่ม Save ต่อ section การ apply ข้าม section
  แล้วกด Save ครั้งเดียวจะได้ค่าที่บันทึกไม่ครบโดยไม่มี error
- **field ที่ cascade** — เปลี่ยนค่าหนึ่งแล้วอีกหลายค่าถูกล้างเงียบ ๆ → verify **ทุก field ในไฟล์**
  หลัง apply เสมอ ไม่ใช่เฉพาะตัวที่เพิ่งแก้ (บทเรียนจาก skill `netsuite-create-record`)
- **dropdown ที่ต้องคลิกจริง** — component ของ NetSuite/Oracle JET ไม่รับ synthetic click ต้องใช้
  `pick` ไม่ใช่ `fill` (`gotchas.md`)
- **session หมดอายุกลางทาง** — apply ไปครึ่งทางแล้วเด้ง login = ระบบอยู่ในสถานะครึ่ง ๆ ·
  ตรวจ url ก่อนเริ่มและหลัง apply ทุกครั้ง เจอเด้ง = หยุดแล้วรายงาน ไม่ใช่ login ใหม่แล้วไปต่อ

## 7. เส้นที่ห้ามข้าม

- **ห้ามใช้โหมดนี้กับสิ่งที่ยังไม่มี desired-state ใน repo** — การแก้ที่ไม่มีไฟล์กำกับคือการแก้
  ที่ไม่มีใคร review และไม่มีใครย้อนได้
- **ห้ามให้ `configure` ทำงานเป็นส่วนหนึ่งของ QA run** — QA ต้อง read-only เสมอ ถ้าปนกันเมื่อไหร่
  จะไม่มีใครรู้ว่ารายงาน QA ฉบับนั้นเปลี่ยนอะไรไปบ้าง
